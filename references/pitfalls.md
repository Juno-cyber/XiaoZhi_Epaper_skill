## Common Pitfalls
1. **Text overflow right boundary (the #1 layout bug)**: Before placing ANY text element, compute `x + (chars × char_width) ≤ 291`. Chinese char = 16px at font_size=16, 12px at font_size=12 (English/digit ≈ half). Wrong: `x=200, text="今天天气真好适合出去散步"` → ends at 392. Right: `x=0` → ends at 192. Split-screen right zone (186-296, 110px) fits only **6 chars at 16px** / 9 at 12px. If text won't fit at current x: (a) start at x=0 for full width, (b) shorten text, or (c) split into multiple lines at different y.

2. **mDNS not resolving**: Some networks block mDNS. Fall back to port scan: `python3 xiaozhi_discovery.py -v` shows which strategy succeeds.
3. **Port scan slow**: 254 IPs at 0.5s timeout each, parallelized 50-way. Takes 2-5s. If you know the IP, skip discovery and curl directly.
4. **5s response timeout**: The device HTTP server waits 5s for MCP tool completion. Complex tools may time out — retry or simplify the request.
5. **No auth**: Any device on the same LAN can call the API. Only use on trusted networks.
6. **One request at a time**: The device processes MCP calls sequentially. Don't fire concurrent requests.
7. **Browser CORS — "connected but operations fail" = OPTIONS 405**: The #1 symptom of missing CORS support is: health check (GET /) succeeds and shows "已连接", but ALL subsequent operations (POST /api/call) fail with "获取失败". Root cause: the browser sends an `OPTIONS` preflight request before POST, and ESP32 httpd returns `405 Method Not Allowed` because no `HTTP_OPTIONS` handler is registered for that URI. The `HandleOptions()` function may exist in `local_control.cc` but compiler warns `'HandleOptions' defined but not used` — it was never wired to a URI. **Fix (VERIFIED on hardware)**: For each registered URI (`/`, `/mcp`, `/api/call`, `/api/canvas_image`), register a separate `httpd_uri_t` with `.method = HTTP_OPTIONS, .handler = HandleOptions`. Also ensure `config.max_uri_handlers` is large enough (original 5 handlers + 4 OPTIONS = 9, set to 10+). After patching, verify: `curl -X OPTIONS http://<IP>:8080/api/call -H "Origin: http://test" -H "Access-Control-Request-Method: POST"` should return 200/204 with `Access-Control-Allow-Origin: *`. Either (a) patch firmware CORS + OPTIONS handlers, or (b) use a reverse proxy (Nginx/Python) to avoid CORS. See `references/web-console.md` for details.
8. **Recipe `extra_ingredients` was unreliable (now fixed)**: As of v2.0.3+ the device auto-checks fridge inventory. In `fridge_only` mode, if any required ingredient is missing, the call is **rejected** with a message like `"fridge_only mode requires all ingredients to be in the fridge. Missing: 泡椒、牛肉"`. In `mixed_purchase` mode, missing ingredients are auto-filled into `extra_ingredients`. The response also includes a `missing_ingredients` field. Older firmware returned empty `extra_ingredients` — if you encounter an old firmware, cross-reference `required_ingredients` against `current_fridge_items` yourself.
9. **Canvas layout persistence & label management**: Canvas text/lines/rects/images are auto-saved to `/canvas/layout.json` in LittleFS on every `add`/`remove`/`clear` operation, and restored on boot. Images uploaded via `POST /api/canvas_image` also persist in LittleFS. Both survive power cycles. Image persistence works because `EpaperLabel` stores `image_name[32]` — `SaveCanvasLayout` writes `{"type":"image","name":"...","x":..,"y":..,"w":..,"h":..}` and `LoadCanvasLayout` re-reads the bitmap file from `/canvas/<name>` on restore. **Label count limit**: max 30 canvas labels. Adding beyond 30 returns `"Canvas label limit reached (30). Call fridge.canvas.clear first."`. Same-ID `add` is a replacement (doesn't increase count). `canvas.clear` **deletes** `layout.json` (not writes empty array). `SaveCanvasLayout` with 0 labels also deletes the file. This prevents the "ghost label accumulation" bug where repeated add-without-clear causes layout.json to grow unbounded (observed 104 ghost labels → 8KB file).
10. **Canvas label accumulation (max 30)**: Each `add` operation that creates a *new* ID (not replacing an existing one) increments the canvas label count. The device enforces a **30-label limit** — exceeding it returns `"Canvas label limit reached (30). Call fridge.canvas.clear first."` Same-ID adds are replacements and don't count toward the limit. Always call `fridge.canvas.clear` before drawing a new layout to avoid invisible stale labels accumulating from previous sessions (they overlap visually but still consume memory and inflate `layout.json`).
11. **`canvas.clear` deletes layout.json**: `clear` does not write an empty `[]` to `layout.json` — it **deletes the file entirely** via `unlink()`. Similarly, `SaveCanvasLayout()` deletes the file when there are 0 canvas labels. This prevents the file from growing unbounded across reboots.
12. **`fridge.pagemanager` now supports pages 1-15**: The `target_page` property accepts 1-15. Pages 1-5 are system pages, 6 is the default canvas, 7-15 are user-created custom pages. When adding new system pages, update both the Property max and the HandlePageManager range check.
13. **Partition table change for LittleFS**: Adding the `canvas_data` partition requires changing `partitions/v2/16m.csv` — the `assets` partition shrinks from 8MB to 6MB, and `canvas_data` takes the last 2MB (offset `0xE00000`). After changing the partition table, do a **full clean** (`idf.py fullclean`) and flash **all** partitions (bootloader + partition_table + ota_data + xiaozhi.bin + assets.bin), not just the app.
14. **LoadCanvasLayout timing**: `LoadCanvasLayout()` must NOT be called in `FridgeMcpTools::Initialize()` — LittleFS isn't mounted yet at that point (mount happens in `LocalControl::Start()` after WiFi connects). Call it from `LocalControl::MountCanvasStorage()` after `esp_vfs_littlefs_register()` succeeds, via `FridgeMcpTools::RestoreCanvasLayout()`. Symptoms if called too early: `fopen("/canvas/layout.json")` silently fails, layout not restored, no error in log.
15. **JSON field parsing offset**: When parsing `"font_size":` and `"max_width":` from layout.json, the offset is `pos + 12` (11 chars for the key name + 1 for the colon), NOT `pos + 13`. An off-by-one here causes `font_size` to default to 0, making text render with the smallest font after reboot.
16. **Canvas label accumulation without clear**: If you add canvas elements without calling `canvas.clear` first, labels accumulate across reboots (LoadCanvasLayout restores old ones, then new adds pile on top). Visually invisible because overlapping controls cover each other, but `layout.json` grows unbounded (observed 104 phantom labels = 8KB file). **Always call `canvas.clear refresh=false` before placing a new layout.** The firmware now enforces a 30-label limit via `CheckCanvasLabelLimit()` — exceeding returns `"Canvas label limit reached (30). Call fridge.canvas.clear first."`. Same-ID adds count as replacements, not new entries.
17. **SaveCanvasLayout when 0 labels = delete file**: When all canvas labels are removed (via `canvas.clear` or removing the last one), `SaveCanvasLayout()` calls `unlink()` to delete `layout.json` entirely rather than writing an empty `[]`. This prevents the "phantom accumulation" pattern where an empty layout file still triggers a load path on boot. `canvas.clear` also explicitly `unlink()`s the file.
18. **User prefers tool scripts in the Hermes skill, not the C++ repo**: The user asked why Python scripts (discovery, crash_log) were placed in the xiaozhi-esp32 repo instead of the Hermes skill. **Always put operational/control scripts in `~/.hermes/skills/smart-home/xiaozhi-control/scripts/`**, never in the firmware repo. The firmware repo is for C++ code only. The only Python that belongs in the repo is build-system or test scripts that ship with the upstream project.
19. **HTTPS dev proxy breaks browser navigation**: The Python `proxy_server.py` uses SSL certs (e.g. `ssl/<domain>.pem`) and serves HTTPS on port 9876. Hermes browser tools and Playwright MCP will fail with `ERR_CERT_COMMON_NAME_INVALID` because the cert CN doesn't match `localhost`. **Fix**: for testing, launch a plain HTTP proxy (no SSL) on the same port. Write a minimal `http_proxy.py` that subclasses `SimpleHTTPRequestHandler` and forwards `/xiaozhi-api/` to the device, without wrapping the socket in SSL. This lets browser tools navigate to `http://localhost:9876/xiaozhi.html` without cert issues. For production, use Nginx with a valid cert and `proxy_pass`.
20. **`sudo` is blocked by Hermes safety guards**: Hermes terminal blocks `echo "password" | sudo -S ...` as a brute-force vector, and `sudo -A` (askpass) requires a pre-written askpass script that also gets blocked on timeout. If a package needs installing (e.g. `tmux` for Claude Code interactive mode), ask the user to run the `sudo apt install` command themselves. Do not attempt multiple sudo workarounds — they will all be blocked.
21. **Claude Code `--dangerously-skip-permissions` needs tmux for interactive mode**: Without tmux, interactive Claude Code cannot be orchestrated. But print mode (`-p`) works fine without tmux — it skips all dialogs and exits on completion. **When tmux is unavailable, always use print mode** (`claude -p "task" --max-turns N --allowedTools "..."`).
22. **Claude Code hook errors are non-fatal**: If a project has a `PostToolUse` hook (e.g. `uv run ruff format`) that fails because the tool isn't installed or doesn't apply to the file type (e.g. `.html`/`.js`), Claude Code still writes the file successfully. The hook error is a warning, not a blocker. Don't treat it as a failure.
23. **"Operations fail" after previously working = check device online FIRST**: When the web console shows "已连接" (connected) but operations fail with "获取失败", the root cause is NOT always CORS (pitfall #7). Another common cause: **the ESP32 device has gone offline** (WiFi dropped, power loss, crash). Diagnostic sequence: (1) `ping <IP>` — if 100% packet loss, device is offline; (2) `arp -n <IP>` — if ARP entry shows `(incomplete)`, device is not responding at layer 2; (3) `curl http://<IP>:8080/` — if connection refused/timeout, device HTTP server is down. Only after confirming the device is online should you investigate CORS or code bugs. This was observed in practice: user reported "画布更新提交都失败了" (canvas submissions all failed), root cause was device had dropped off WiFi — not a code issue.
24. **Device offline after flash — check reachability before debugging code**: When the user reports "operations fail" or "获取失败" on the web console, the ESP32 may simply be offline (rebooting after flash, WiFi dropped, power issue). **Diagnostic sequence**: (1) `curl -s --max-time 3 http://<IP>:8080/` — if empty/timeout, device is offline; (2) `ping -c 1 <IP>` — 100% packet loss = offline; (3) `arp -n | grep <IP>` — `(incomplete)` entry = device physically off the network. This is distinct from CORS issues (pitfall #7): CORS = GET health check works but POST fails with 405 on OPTIONS preflight; device offline = even GET fails with 502/connection-refused/no-route. After flashing, wait 5-10s for WiFi reconnection; if still offline after 30s, check device power and WiFi credentials.
25. **`max_uri_handlers` must match total handler count**: The CORS patch registers OPTIONS handlers for each URI. With 5 original handlers (GET /, POST /mcp, POST /api/call, POST /api/canvas_image, GET /api/canvas_image) + 4 OPTIONS handlers = 9 total. But `config.max_uri_handlers = 8` in the current firmware means the 9th handler (OPTIONS /api/canvas_image) silently fails to register (`httpd_register_uri_handler` returns `ESP_ERR_HTTPD_HANDLERS_FULL`). This means canvas image uploads via direct browser-to-device connection (not through proxy) will have CORS preflight fail for `/api/canvas_image`. **Fix (VERIFIED on hardware)**: set `config.max_uri_handlers = 16` in `LocalControl::Start()`. The proxy mode (pitfall #19) masks this because the proxy handles CORS itself, but direct browser-to-device connections need all OPTIONS handlers registered. **Additionally**: `HandleCanvasImageUpload` and `HandleCanvasImageList` must call `SetCorsHeaders(req)` before `httpd_resp_sendstr()` — these were missed in the initial CORS patch (only the error paths had it), causing successful upload responses to lack CORS headers, which browsers reject.
26. **Delegate web design to Claude Code, don't hand-edit**: The user set up Claude Code with `.mcp.json` (Playwright + chrome-devtools MCP) and `CLAUDE.md` project context in the web project directory (`<web-project-dir>`). For ANY web design work (optimizing HTML/CSS/JS, adding new features like freehand drawing or image insertion), delegate to Claude Code via `delegate_task` with `toolsets: ["terminal", "file"]` (or `["browser", "terminal", "file"]` for testing tasks). Do NOT hand-edit HTML/JS files yourself — Claude Code produces better results with its full-file awareness and can run `node --check` for JS syntax validation. The workflow: (1) write a detailed prompt with API contracts and design requirements; (2) `delegate_task` in background; (3) verify the result with Hermes browser tools (`browser_navigate` + `browser_console` expressions to check DOM state and API responses).
27. **Unified canvas event system — multiple listeners on same canvas cause silent failures**: When a canvas serves multiple interaction modes (brush drawing + element dragging + click-to-place preview), DO NOT register separate `mousedown`/`mousemove`/`mouseup` listeners for each mode via `attachFreehandDrawing()` + `attachCanvasCoords()` + `attachElementDragging()`. Multiple listeners on the same element cause event ordering issues and silent hit-test failures — the symptom is "dragging doesn't work" with no error in console. **Fix (VERIFIED)**: Replace all three functions with a single `attachCanvasEvents()` that registers one set of mousedown/mousemove/mouseup/mouseleave/click handlers, with an internal state machine that checks `isBrushActive()` / `state.drag.active` / `state.preview.active` to determine the current mode. See `references/canvas-web-interaction.md` for the full pattern.
28. **`fridge.canvas.control` `action=remove` removes a single element; `action=clear` removes all**: The old `fridge.canvas.remove` tool was merged into `fridge.canvas.clear` to reduce total tool count (see pitfall #48). When `id` is passed and non-empty, only that element is removed; when `id` is omitted or empty, all elements are cleared. The web console should call `fridge.canvas.clear {id: "elem_id"}` to remove a single element. The old `fridge.canvas.list` and `fridge.canvas.refresh` tools were also removed — use `fridge.page.element.list` for listing and pass `refresh=true` on the last batch operation instead of calling a separate refresh tool.
29. **Brush offscreen canvas — prevents freehand strokes from vanishing**: `renderCanvasPreview()` is called on every mousemove (preview mode), mouseleave, and tab switch. It starts with `fillRect(0,0,296,128)` white — wiping ALL visible canvas pixels. If brush strokes are drawn directly on the visible canvas, they vanish instantly. **Fix (VERIFIED)**: use `state.brush.offscreen` (a 296×128 offscreen `<canvas>`) as a persistent backing store. `drawBrushDot`/`drawBrushSegment` draw to BOTH visible and offscreen. `renderCanvasPreview()` composites the offscreen on top at the end: `ctx.drawImage(state.brush.offscreen, 0, 0)`. `submitFreehandToScreen()` reads pixels from the OFFSCREEN (not visible) canvas to avoid grid/element contamination. See `references/canvas-web-interaction.md` § "Brush Offscreen Canvas".
30. **Decoupled submit model — reduce e-paper refresh to extend lifespan**: Clicking on the canvas to place text/rect/line should fill coordinate inputs and show a preview only, NOT auto-submit to the device. The user clicks the corresponding "添加" button to sync. This reduces e-paper refresh frequency (each refresh wears the screen). For lines, use a `lineReady` state after two clicks: the full preview stays visible until the button is pressed. See `references/canvas-web-interaction.md` § "Click-to-Place Preview (Decoupled Submit Model)".
31. **Rect default size should be small**: The rect tool's default `w`/`h` in the HTML should be small (e.g. 40×30), not large (280×60). A large default covers most of the 296×128 canvas and is rarely what the user wants — they usually need small boxes.
32. **Preview must survive mouseleave — don't deactivate on leave**: `onCanvasMouseLeave` must NOT set `state.preview.active = false`. If it does, placed previews (text/rect/line) vanish the moment the cursor leaves the canvas — the user clicks to place a rect, moves to the input fields to tweak w/h, and the preview is gone. Only tool switch, Esc key, or successful button-submit should reset `preview.active`. The mouseleave handler should still clear the coordinate display and call `renderCanvasPreview()` + `renderPreview()` to redraw the persistent preview without the mouse-following overlay. See `references/canvas-web-interaction.md` § "Preview Persistence After Mouse Leave".
33. **onCanvasClick must activate preview, not just fill inputs**: When the user clicks to place a text/rect, `onCanvasClick` should do `state.preview.x = cp.x; state.preview.y = cp.y; state.preview.active = true; renderCanvasPreview(); renderPreview()` — NOT just `fillCoordsToInputs()`. If you only fill inputs without activating the preview, the preview never shows until the mouse re-enters the canvas.
34. **Input field changes should trigger live preview update**: When the user adjusts `textText`, `textFont`, `rectW`, `rectH`, `rectFilled`, `lineWidth` etc. after placing a preview, the preview should update in real-time. Add `'input'`/`'change'` listeners on those fields that call `renderCanvasPreview()` + `renderPreview()` when `state.preview.active && !isBrushActive()`.
35. **Use clamped coords for preview position**: In `onCanvasMouseMove` and `onCanvasClick`, use `clampCanvasPoint()` output for `state.preview.x/y`, not raw `p.x/p.y`. Raw values can extend beyond [0,295]/[0,127], causing the preview to be drawn partially off-screen.
36. **Use `Promise.allSettled` for multi-API parallel fetches, not `Promise.all`**: When loading fridge data (`fridge.stats.summary` + `fridge.item.list` in parallel), `Promise.all` rejects entirely if either call fails — the user sees "加载冰箱数据失败" even if only one API is down. `Promise.allSettled` lets each succeed/fail independently: render whichever data arrived, show a partial-error toast for the one that failed. This pattern applies to any `Promise.all` over independent API calls where partial results are still useful to the user.

37. **`fridge.page.element.control` (action=`add`) requires `x`/`y` even for `line` type**: The `x` and `y` parameters are declared as required (`Property("x", kPropertyTypeInteger, 0, 295)` without a default) in the MCP tool registration. For `text` and `rect` types, `x`/`y` is the element position — intuitive. But for `line` type, the actual coordinates are `x1`/`y1`/`x2`/`y2` — `x`/`y` are unused but still required by the schema. Omitting them causes `"Missing valid argument: x"` error. **Workaround**: always pass `x:0, y:0` (or any valid value) when adding a line element. The web UI should auto-fill these when the user selects `line` type.

38. **`fridge.page.element.control` (action=`add`) parameters are FLAT, not nested under `element`**: The MCP tool accepts `page`, `id`, `type`, `x`, `y`, `text`, etc. as top-level keys in the `args` object. Passing `{"element": {"type":"text", "id":"title", ...}}` returns `{"error":"Missing valid argument: id"}` because the tool looks for `id` at the top level of args, not inside an `element` sub-object. **Correct format**: `{"page":7, "id":"title", "type":"text", "text":"待办事项", "x":8, "y":2, "font_size":12, "align":"left", "refresh":false}`. All params are siblings, never nested.

39. **Don't hand-curl individual element adds — use the template or quick_page_builder**: When building a custom page layout (especially a todo list), the skill ships `templates/todo-list-page.sh` (ready-made todo layout: clears, adds 9 elements, switches page in one pass) and `scripts/quick_page_builder.py` (DSL-driven batch deployment). Hand-curling 9+ individual `curl -X POST /api/call` commands is slow (~2s each), error-prone (easy to nest params wrong — see pitfall #38), and wastes conversation turns. **Always check if a template exists first**: `ls ~/.hermes/skills/smart-home/xiaozhi-control/templates/`. For todo pages specifically, run `bash ~/.hermes/skills/smart-home/xiaozhi-control/templates/todo-list-page.sh <IP> <PAGE>` then use `fridge.page.element.update` to set the item text. Only hand-curl when no template fits and the layout is highly custom (in which case use `quick_page_builder.py` with a `.layout` file).
40. **Two API formats for MCP tool calls — know which endpoint uses which**: The device has two HTTP endpoints for MCP calls: `/api/call` uses `{"tool":"...","args":{}}` format (simplified, by `local_control.cc`), while `/mcp` uses JSON-RPC `{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"...","arguments":{}}}` format. Mixing them up returns `{"error":"Missing 'tool' field"}`. For curl testing, always use `/api/call` with the simplified format — it's shorter and doesn't require an incrementing `id` field.
41. **Claude Code `-p` background process produces no stdout — timeout without output**: When launching `claude -p "..." --dangerously-skip-permissions` as a `terminal(background=true)` process, the process runs (high CPU usage, files get modified on disk) but **produces zero stdout output** even after completion. `process(action="poll")` shows empty `output_preview` and `process(action="log")` returns 0 lines. This is because `claude -p` in non-interactive mode buffers all output until exit, and in background mode the shell setup may lose the stdout pipe. **Workaround**: for simple file edits that follow a clear spec (API contract, exact HTML/JS changes), do the edits yourself with `patch` tool — it's faster and more reliable than delegating to Claude Code for straightforward changes. Reserve Claude Code delegation for complex multi-file design work where its full-file awareness provides genuine value.
42. **CMake `**/*.cc` glob DOES pick up new subdirectory files — but requires `idf.py fullclean` + `touch CMakeLists.txt`**: When adding a new `.cc` file in an existing subdirectory (e.g., `Fridge/custom_page_manager.cc` alongside `Fridge/fridge_mcp.cc`), the `file(GLOB ... **/*.cc)` pattern in `main/CMakeLists.txt` should pick it up. But a stale build cache may not. Symptoms: the `.obj` file is created (visible in `build/.../Fridge/`), `nm` shows the symbols, but the linker still reports `undefined reference`. **Fix (VERIFIED)**: (1) `idf.py fullclean` to wipe all build artifacts, (2) `touch main/CMakeLists.txt` to force CMake re-glob on next configure, (3) `idf.py build`. After this, the new `.cc` is properly compiled and linked.
43. **Two API formats — `/api/call` vs `/mcp`**: The device has two HTTP endpoints: `/api/call` uses `{"tool":"...","args":{}}` (simplified), while `/mcp` uses JSON-RPC `{"jsonrpc":"2.0","id":N,"method":"tools/call","params":{"name":"...","arguments":{}}}`. Mixing them returns `{"error":"Missing 'tool' field"}`. For curl testing, always use `/api/call` with the simplified format — it's shorter and doesn't need an incrementing `id`. The web console JS also uses `/api/call`.
44. **Device reboot via HTTP**: The device doesn't have a `/api/reboot` endpoint. To reboot for persistence testing, use the ESP32 `esp_restart()` function via a custom MCP tool, or simply power-cycle the device. The `/api/reboot` URI returns `{"error":"Nothing matches the given URI"}`.
45. **CustomPageManager singleton — must define `GetInstance()` in `.cc`**: When creating a new C++ singleton class in the ESP-IDF project, declaring `static CustomPageManager& GetInstance();` in the `.h` is NOT enough. You must also define it in the `.cc`: `CustomPageManager& CustomPageManager::GetInstance() { static CustomPageManager instance; return instance; }`. The compiler compiles the `.cc` successfully and the `.obj` is created, but the LINKER fails with `undefined reference to _ZN17CustomPageManager11GetInstanceEv`. Use `nm <file>.obj | grep GetInstance` to diagnose: `W` (weak) but no `T` (text) = definition missing. This pitfall is also captured in `esp-idf-embedded-development` skill pitfall #15.
- **`esptool` flash via `@flash_args` must run from `build/` dir**: When `idf.py flash` is blocked by timeout, use `esptool` directly: `cd build && python3 -m esptool --chip esp32s3 -b 460800 --before default_reset --after hard_reset -p /dev/ttyUSB0 write_flash @flash_args`. The `@flash_args` file is in `build/flash_args` and contains relative paths (`bootloader/bootloader.bin`), so the command MUST run from `build/`. Running from the project root gives `No such file or directory: 'bootloader/bootloader.bin'`.
- **Serial port busy after `idf.py monitor` or `cat`**: If `esptool` reports `Could not exclusively lock port`, kill the process holding the port: `fuser -k /dev/ttyUSB0`, wait 1-2s, then retry. The `cat /dev/ttyUSB0` approach for crash log capture holds the port open and blocks subsequent flash attempts.
- **`idf.py flash` and `idf.py monitor` timeout in non-TTY Hermes terminal**: The `idf.py` wrapper expects an interactive terminal (TTY) for flash and monitor operations, and may hang indefinitely or timeout in Hermes's non-interactive shell. **Workaround**: use `esptool` directly (pitfall #39) for flashing, and `stty + cat` or the `crash_log.py` script for serial output capture. Do NOT attempt `idf.py -p /dev/ttyUSB0 flash` — it will timeout. Use `python3 -m esptool ... write_flash @flash_args` from the `build/` directory instead.
- **Debugging ESP32 crashes with addr2line**: When the device enters a crash loop (`Guru Meditation Error`), capture the serial log via `crash_log.py`, then map backtrace addresses to source lines with `xtensa-esp32s3-elf-addr2line -pfiaC -e build/xiaozhi.elf 0x<addr1> 0x<addr2> ...`. This immediately reveals the crash function and file:line. See `references/firmware-development.md` § Debugging Crashes with addr2line for the full workflow.
- **`SetDeviceState(kDeviceStateStarting)` crash — do NOT call `audio_service_` methods**: When adding code to the `kDeviceStateStarting` or `kDeviceStateWifiConfiguring` cases in `SetDeviceState()`, do NOT call `audio_service_.EnableVoiceProcessing()`, `audio_service_.EnableWakeWordDetection()`, `display->SetStatus()`, or `display->SetEmotion()`. `SetDeviceState(kDeviceStateStarting)` is the first call in `Application::Start()` (line 367), before `audio_service_.Initialize()` (line 380). Calling methods on the uninitialized `unique_ptr<AudioProcessor>` causes `LoadProhibited` crash → boot loop. **Only call `display_epaper->SetPage(CHAT_PAGE)` in those cases.** The status/emotion/audio setup is handled later in the normal state flow (e.g. `kDeviceStateIdle`). See `references/firmware-development.md` § Device State & E-Paper Page Auto-Switch for full details.
- **Hiding e-paper UI elements via `visible=false`**: To hide a label on a page without removing it (preserving runtime toggle), change the `visible` parameter from `true` to `false` in the `EpaperLabel::Text/Bitmap/Line()` factory call inside `SetupUI()`. This is cleaner than commenting out `AddLabel()` lines. See `references/firmware-development.md` § E-Paper Chat Page Layout Customization for the factory parameter order and available fonts/emoji bitmaps.
46. **Custom page persistence — three bugs must ALL be fixed**: Custom page content disappearing after reboot has three independent causes, all of which must be fixed for persistence to work:
    - **Bug A**: `UpdateElementText()` doesn't call `SavePageLayout()` → text updates lost (fix: add `SavePageLayout(page)` call)
    - **Bug B**: `LoadPageLayout()` parser matches the outer JSON wrapper `{}` instead of element objects → only 0-1 elements restored (fix: `strstr(buf, "[")` to skip wrapper)
    - **Bug C**: `RestoreCanvasLayout()` called from WiFi pthread → stack overflow crash loop (fix: wrap in `xTaskCreate` with 16KB stack)
    All three were discovered in the same session. Fixing only one is insufficient — the device will either crash (C), restore incomplete elements (B), or lose text updates (A).
47. **Don't notify user about xiaozhi cronjob results**: The user stated they don't want to be notified about xiaozhi-related cronjob execution results. They will ask when they need the information. Set cron jobs to `deliver: "local"` (silent) or `deliver: "origin"` without proactively reporting results unless asked.
48. **MCP tool count limit — xiaozhi server caps at 32 tools**: The xiaozhi MQTT server enforces a **hard limit of 32 MCP tools** per device. When exceeded, the server returns an error message `"The number of tools has reached the limit: 32"` which triggers `protocol_->OnNetworkError()` → `Alert(Error, ...)` on the e-paper display (shows "Error" text with 😞 emoji). The error also plays a warning sound via `audio_service_.PlaySound()`, which blocks the main event loop, causing secondary `AFE: Ringbuffer of AFE(FEED) is full` warnings on first wake word invocation (audio feed task can't consume data while the main loop is blocked). **Current tool count (after fix)**: 3 common (`self.get_device_status`, `self.audio_speaker.set_volume`, `self.screen.set_brightness`) + 2 user-only (`self.get_system_info`, `self.reboot`) + 3 lamp (`self.lamp.*`) + 24 fridge (10 fridge + 5 canvas + 9 custom page) = **32 tools = exactly the limit**. Canvas tools were reduced from 8 to 5 by removing `fridge.canvas.list` (use `page.element.list`), `fridge.canvas.refresh` (pass `refresh=true` on last operation), and `fridge.canvas.remove` (merged into `canvas.clear` with optional `id` param). **Diagnosis**: capture serial log with `crash_log.py`, look for `Alert [sad] Error: The number of tools has reached the limit: 32` after `MQTT: Connected to endpoint`. The error appears ~3-4 seconds after MQTT connection is established, when the server processes the `tools/list` response and rejects the registration.
49. **`SetDeviceState(kDeviceStateStarting)` is called BEFORE `audio_service_` is initialized — do NOT call audio methods in early states**: `Application::Start()` calls `SetDeviceState(kDeviceStateStarting)` at line 367, but `audio_service_.Initialize()` happens later at line 380. If you add code to the `kDeviceStateStarting` or `kDeviceStateWifiConfiguring` cases in `SetDeviceState()` (the switch at line ~738), you must NOT call `audio_service_.EnableVoiceProcessing()`, `audio_service_.EnableWakeWordDetection()`, or any other `audio_service_` method — the `unique_ptr` is still null and dereferencing it causes a `LoadProhibited` crash (EXCVADDR=0x00000000). Backtrace: `AudioService::EnableVoiceProcessing → Application::SetDeviceState → Application::Start → app_main`. **Safe operations** in these early states: `display_epaper->SetPage()`, `display_epaper->SetStatus()`, `display_epaper->SetEmotion()`, `display_epaper->SetChatMessage()` — these use the epaper display which IS initialized earlier in the constructor. **Diagnose** with: `xtensa-esp32s3-elf-addr2line -pfiaC -e build/xiaozhi.elf <backtrace_addrs>` to map crash addresses to source lines. This pitfall was discovered when adding auto-switch-to-CHAT_PAGE logic for config mode: the first version included `audio_service_.EnableVoiceProcessing(false)` in the `kDeviceStateStarting` case, causing a boot loop crash. Fix: only call `display_epaper->SetPage(CHAT_PAGE)` in the early states; leave audio/wake-word setup to the `kDeviceStateIdle` case which runs later.
50. **Wake word blocking fix — AfeWakeWord::Feed() must check DETECTION_RUNNING_EVENT**: When `AudioDetectionTask` detects a wake word, it calls `Stop()` which clears `DETECTION_RUNNING_EVENT` on its own `event_group_`. However, `AudioService`'s `AS_EVENT_WAKE_WORD_RUNNING` bit stays set, so `AudioInputTask` keeps calling `Feed()` — which feeds data into an AFE whose `fetch()` side has stopped, overflowing the AFE ringbuffer. This produces hundreds of `AFE: Ringbuffer of AFE(FEED) is full` warnings over 5+ seconds, blocking MQTT handshake and UDP channel setup, delaying wake response from ~1.3s to 5+ seconds. **Fix**: in `AfeWakeWord::Feed()`, check `xEventGroupGetBits(event_group_) & DETECTION_RUNNING_EVENT` and return early if not set — the AFE consumer is gone, feeding it only floods the ringbuffer. **Do NOT try to fix this in `Application::OnWakeWordDetected()` by calling `audio_service_.EnableWakeWordDetection(false)` — that path blocks the subsequent `EnableWakeWordDetection(true)` re-initialization and makes wake word detection die entirely after the first wake.** The correct fix is at the Feed() source, not the state-machine caller. Symptom of the failed approach: the device stops responding to wake words entirely, and the serial log shows no wake events after the first one. **Per-task doc**: see the `feishu-docs` skill `references/todo-table.md` for the doc pattern. See `references/firmware-development.md` § Wake Word Blocking for the full root-cause analysis, including the `AudioDetectionTask` → `Stop()` → `DETECTION_RUNNING_EVENT` clear path, and the `AudioInputTask` → `Feed()` → ringbuffer overflow loop.

52. **ESP32 `align=center` treats `x` as left edge of centering region, not text center — differs from HTML Canvas**: When using `align=center` with `fridge.canvas.add_text` or `fridge.page.element.add`, the ESP32 firmware centers text within `[x, x+max_width]`, where `max_width` defaults to 276. This means `x=148` does NOT center text at pixel 148 — instead it centers within [148, 424], causing text to appear far right on the 296px screen. **To truly center text on screen**: use `x=0` or `x=10` with `align=center` (centering region covers the full width). **HTML Canvas discrepancy**: `ctx.textAlign='center'` treats `x` as the text's center point, so `fillText(text, 148, y)` correctly centers at pixel 148. The web console `renderCanvasPreview()` must compensate for this difference: for `align=center`, compute `drawX = elem.x + (elem.max_width || 276) / 2`; for `align=right`, compute `drawX = elem.x + (elem.max_width || 276)`. Without this compensation, the web preview shows centered text correctly while the actual e-paper display shows it shifted far right. **Root cause**: the ESP32 `drawText` implementation with `align=center` calculates the text start position as `x + (max_width - text_width) / 2`, treating `x` as the region's left edge, while `max_width` is not exposed as an MCP parameter (hardcoded to 276). This was discovered when user reported "居中文字跑到最右边" (centered text shifted to the far right) — the web preview looked correct but the physical screen showed the text shifted right.
53. **Firmware v2.0.5 — aggregator tools (`fridge.canvas.control`, `fridge.page.control`) are NOT registered; use legacy names**: The current flashed firmware (bread-compact-wifi-epaperx v2.0.5) does NOT register the aggregator dispatch tools. Calling them returns `{"error":{"message":"Unknown tool: fridge.canvas.control"}}`. Consequently `scripts/quick_page_builder.py` (which dispatches via the aggregator) **fails silently** on this firmware — the agent believes it deployed (all curl calls return HTTP 200 JSON-RPC) but the screen never changes. **Verified working via `/api/call`** (legacy single-point names): `fridge.canvas.add_text`, `fridge.canvas.add_line`, `fridge.canvas.add_rect`, `fridge.canvas.add_image`, `fridge.canvas.remove`, `fridge.canvas.clear`, `fridge.canvas.refresh`, `fridge.canvas.list`. Also verified: `fridge.pagemanager`, `fridge.stats.summary`, `fridge.stats.query`. **Rule**: on this firmware, always hand-curl legacy `fridge.canvas.*` names with `refresh=false` on all adds + a final `fridge.canvas.refresh`. Check each response for `"status":"success"` — do not trust exit code 0. Diagnose a silent no-op screen by calling `fridge.canvas.list` and comparing to what you intended to deploy.
54. **Firmware font (u8g2 wqy gb2312) has NO glyph for U+00B7 (·) — it renders as nothing; use ASCII `-` instead**: The device renders text with `u8g2_font_wqy12_t_gb2312` / `u8g2_font_wqy16_t_gb2312` (WenQuanYi GB2312 bitmaps). Field test (2026-08-05): pushing `一言·霍华德·菲利普·洛夫克拉夫特` to the canvas stored the text verbatim on device (`fridge.canvas.list` returns the `·` intact) but the physical e-paper screen showed `一言霍华德菲利普洛夫克拉夫特` — U+00B7 is silently dropped at render time. A test row `A|B-C—D・E·F｜G，H` showed: ASCII (`|`, `-`), `・` (U+30FB), `｜` (U+FF5C), `，` (U+FF0C) all render; `—` (U+2014) and `·` (U+00B7) do NOT. However U+30FB (・) renders **tiny and cramped** against the previous character — user rejected it visually. **Rule**: never put U+00B7 or U+30FB in canvas text; use ASCII `-` as the separator. `quote_fetcher.py` `fmt_source()` joins with `-` so every source string (e.g. `一言-红楼梦`) renders correctly. When writing layout text by hand, stick to ASCII + common GB2312 punctuation; verify any exotic punctuation on the physical screen before shipping.
